# M0 작업 명세 — 기반

- 상위 문서: [PRD](../PRD.md) 9.1절, [SRD](../SRD.md) 1·5·7·8절
- 끝났을 때의 상태: 고려대 메일로 가입하고 프로필을 만든 뒤, 빈 탭 3개가 있는 홈에 들어갈 수 있다. 앱을 껐다 켜도 로그인이 유지된다.

AI 코딩 도구에는 이 문서 한 장을 준다. 여기에 없는 기능(세션, 친구, 할 일, 비서)은 M0에서 만들지 않는다.

---

## 1. 사람이 먼저 준비할 것

코드로 해결되지 않는 항목이다. 끝나야 구현을 시작할 수 있다.

| 항목 | 내용 |
|---|---|
| 앱 이름과 번들 ID | 예: `kr.ac.korea.<이름>` 형식이 아니라 본인 소유 도메인 기준으로 정한다 |
| Apple 개발자 계정 | 실물 기기 설치와 TestFlight에 필요 |
| Supabase 프로젝트 | 리전은 서울. 프로젝트 주소와 공개용 키를 받아 둔다 |
| 메일 발송 서비스 | 발송 도메인 인증(SPF, DKIM)까지 마친다. Supabase 기본 발송은 발송량 제한이 낮아 쓰지 않는다 |
| 메일 수신 확인 | 실제 @korea.ac.kr 주소 3개 이상으로 인증 코드가 받은편지함에 오는지 확인한다(사전 검증) |
| 학과 목록 | 고려대 학과 이름 목록을 표로 준비한다 |

## 2. 범위

| 포함 | 제외 |
|---|---|
| 메일 인증 코드 가입·로그인 | 소셜 로그인, 비밀번호 |
| 가입 도메인 제한 | 다른 학교 추가 화면 |
| 프로필 만들기·수정 | 프로필 사진 올리기(M1에서 카메라와 함께) |
| 탭 3개(오늘, 함께, 기록)의 빈 껍데기 | 탭 안의 실제 내용 |
| 로그아웃 | 계정 삭제(M5) |

## 3. 서버

### 3.1 테이블 (마이그레이션 파일로 작성)

```sql
schools      (id uuid pk, name text not null, email_domains text[] not null, created_at timestamptz default now())
departments  (id uuid pk, school_id uuid not null references schools, name text not null, unique (school_id, name))
profiles     (id uuid pk references auth.users on delete cascade,
              school_id uuid not null references schools,
              handle text not null,
              display_name text not null,
              department_id uuid references departments,
              avatar_path text,
              created_at timestamptz default now(),
              updated_at timestamptz default now())
```

- `handle`은 영문 소문자, 숫자, 밑줄만, 3~20자. 대소문자 구분 없이 고유(`lower(handle)` 고유 인덱스).
- `display_name`은 1~20자.
- 초기 데이터: `schools`에 고려대 1행(`email_domains = {korea.ac.kr}`), `departments`에 준비한 학과 목록.

### 3.2 가입 도메인 제한

- 메일 주소의 도메인이 `schools.email_domains`에 없으면 **서버에서** 가입을 거절한다. 앱의 입력 검사는 편의일 뿐 보안이 아니다.
- 구현 위치: 인증 서비스의 "사용자 생성 전" 훅(DB 함수). 이 훅을 쓸 수 없으면 `auth.users` 삽입 트리거로 대신한다.
- 비교는 소문자로 바꾼 뒤 정확히 일치할 때만 통과. `korea.ac.kr.evil.com`, `xkorea.ac.kr` 같은 주소는 거절되어야 한다.
- 거절 메시지: "고려대학교 메일(@korea.ac.kr)만 가입할 수 있어요."

### 3.3 함수

| 함수 | 입력 | 출력 | 규칙 |
|---|---|---|---|
| `get_my_profile()` | 없음 | 프로필 1행 또는 null | 로그인한 본인 것만 |
| `is_handle_available(handle)` | text | boolean | 형식이 틀리면 false |
| `upsert_my_profile(handle, display_name, department_id)` | text, text, uuid 또는 null | 프로필 1행 | `school_id`는 입력받지 않고 메일 도메인으로 서버가 정한다. 형식 위반이나 중복이면 이유가 담긴 오류 |
| `list_departments()` | 없음 | id, name 목록 | 본인 학교 것만 |

### 3.4 접근 규칙

| 테이블 | 읽기 | 쓰기 |
|---|---|---|
| `schools`, `departments` | 로그인한 사용자 | 불가(관리자만) |
| `profiles` | 같은 학교의 로그인한 사용자. `handle`, `display_name`, `department_id`, `avatar_path`만 | 본인 행만, `upsert_my_profile`을 통해서만 |

앱은 테이블에 직접 쓰지 않는다. 직접 쓰기 권한은 주지 않는다.

### 3.5 인증 설정

- 방식: 메일로 6자리 코드 발송, 코드 입력으로 로그인. 링크 방식은 쓰지 않는다(학교 메일의 링크 검사가 코드를 소모시킬 수 있다).
- 코드 유효 시간 10분. 재전송은 60초에 한 번.
- 메일 제목과 본문은 한국어, 코드가 제목에도 보이게 한다.

## 4. 앱

### 4.1 화면

| 화면 | 요소 | 상태 |
|---|---|---|
| 메일 입력 | 메일 입력칸, `인증 코드 받기` | 형식 오류, 다른 도메인, 전송 중, 전송 실패 |
| 코드 입력 | 6자리 입력칸, `다시 보내기`(60초 대기 표시), 메일 주소 고치기 | 틀린 코드, 만료된 코드, 확인 중 |
| 프로필 만들기 | 아이디, 이름, 학과 선택(검색 가능, 건너뛰기 가능), `시작하기` | 아이디 중복, 형식 오류, 저장 중 |
| 홈 | 탭 3개: 오늘, 함께, 기록. 각 탭은 제목과 "준비 중" 문구만 | — |
| 설정 | 내 프로필 보기·수정, 로그아웃 | — |

진입 규칙: 로그인 정보 없음 → 메일 입력. 로그인됐지만 프로필 없음 → 프로필 만들기. 둘 다 있음 → 홈.

### 4.2 구조

```
App/            진입점, 화면 전환 규칙
Features/Auth/  메일 입력, 코드 입력
Features/Profile/
Features/Home/  탭 껍데기
Core/Backend/   Supabase 호출을 감싼 한 곳. 화면은 여기만 부른다
Core/Store/     기기 저장(SwiftData): 내 프로필 캐시
Config/         프로젝트 주소와 공개용 키(빌드 설정에서 주입)
```

- 최소 지원 iOS 17. 외부 라이브러리는 Supabase Swift SDK 하나만.
- 화면은 `Core/Backend`의 함수만 부르고 SDK를 직접 부르지 않는다. 나중에 서버 함수가 바뀌어도 고칠 곳이 한 군데가 된다.
- 내 프로필은 기기에 저장해 두고, 앱을 켜면 저장분으로 먼저 화면을 그린 뒤 서버 값으로 갱신한다.
- 아이디 중복 확인은 입력이 0.3초 멈춘 뒤 요청하고, 이전 요청은 취소한다.
- 모든 요청에 시간 제한 10초. 실패하면 다시 시도 버튼을 보여 준다.

## 5. 통과 조건

### 5.1 서버 테스트 (자동, 앱 없이 실행)

1. `a@korea.ac.kr` 가입 요청은 받아들여진다.
2. `a@gmail.com`, `a@korea.ac.kr.evil.com`, `a@xkorea.ac.kr`, `a@KOREA.AC.KR.evil.com` 가입 요청은 거절된다.
3. `A@Korea.AC.kr`처럼 대소문자가 섞인 고려대 주소는 받아들여진다.
4. 사용자 A는 `upsert_my_profile`로 자기 프로필을 만들 수 있고, `school_id`는 고려대로 정해진다.
5. 사용자 B가 A와 같은 아이디(대소문자만 다른 경우 포함)를 쓰면 거절된다.
6. 아이디 `ab`, `한글아이디`, `has space`, 21자 이상은 거절된다.
7. 사용자 B는 `profiles`에 직접 insert, update, delete를 할 수 없다. A의 행도, 자기 행도.
8. 로그인하지 않은 요청은 `profiles`, `departments`를 읽을 수 없다.
9. 사용자 B가 A의 프로필을 읽으면 허용된 4개 열만 보인다.

### 5.2 앱 확인 (실물 기기)

1. 처음 설치 → 메일 입력 → 코드 입력 → 프로필 만들기 → 홈까지 막힘 없이 진행된다.
2. 앱을 완전히 끄고 다시 켜면 바로 홈이 뜬다.
3. 비행기 모드에서 켜도 홈이 뜨고(저장된 프로필), 요청이 필요한 동작에는 안내가 나온다.
4. 틀린 코드를 넣으면 안내가 나오고 다시 입력할 수 있다.
5. 로그아웃하면 메일 입력 화면으로 돌아가고 기기에 저장된 프로필이 지워진다.
6. 기준 기기(iPhone XR 또는 SE 2세대급)에서 앱 실행 후 첫 화면까지 2초 이내.
7. 느린 통신(3G 설정)에서 `인증 코드 받기`를 누르면 0.1초 안에 버튼이 진행 상태로 바뀐다.

### 5.3 커밋 전 확인

- 저장소 전체에서 관리자 키(`service_role`)와 발송 서비스 키가 검색되지 않는다.
- 앱에 들어간 키는 공개용 키 하나뿐이다.
- DB 변경이 전부 마이그레이션 파일에 있다. 화면에서 직접 고친 것이 없다.

## 6. 작업 순서

1. 마이그레이션과 초기 데이터
2. 5.1의 서버 테스트 작성 → 전부 실패하는 것 확인
3. 도메인 제한, 함수, 접근 규칙 구현 → 테스트 통과
4. 앱 프로젝트 생성, `Core/Backend`와 화면 전환 규칙
5. 화면 5개
6. 5.2 실물 확인, 5.3 확인

# 흐름 A 작업 지시

당신은 kim1188/pondu 저장소에서 병렬 구현의 한 흐름을 맡았습니다. 대학생 실행 기록 앱(iPhone 앱 + Supabase 서버)을 아홉 개 흐름이 동시에 만들고 있고, 당신은 그중 흐름 A(auth-profile)입니다. 이 세션을 지켜보는 사람은 없으니 질문하지 말고 합리적으로 결정한 뒤 보고에 적으세요.

먼저 읽을 것
- docs/specs/CONTRACT.md 전체. 흐름 사이의 약속이고, 함수 이름·인자·반환 모양·오류 코드·소유 경로가 여기 있습니다. 그대로 따르세요.
- docs/SRD.md, docs/PRD.md 중 당신 흐름에 해당하는 절. docs/specs/M0.md 3절과 5.1절이 당신 흐름의 상세 명세입니다.

작업 규칙
- 브랜치 `ws/a-auth-profile`에서 작업합니다(main에서 분기). 이 브랜치에만 커밋하고 푸시하세요. main에는 푸시하지 않고, 풀 리퀘스트도 만들지 않습니다.
- 계약 1절의 소유 경로만 고칩니다. 다른 흐름의 경로나 0001_schema.sql, docs/는 고치지 않습니다. 계약이 틀렸거나 부족하면 고치지 말고 보고에 "계약 변경 제안"으로 적으세요.
- 다른 흐름의 코드는 당신 브랜치에 없습니다. 그 흐름이 계약대로 만들 것이라 믿고 이름만 맞춰 쓰세요.
- 작업 단위마다 커밋하고, 끝나기 전에 반드시 푸시하세요. 컨테이너는 사라집니다.
- 커밋 메시지나 코드에 모델 이름을 적지 않습니다.

서버 흐름 공통
- 일반 Postgres 16이 설치되어 있습니다. `supabase/tests/run.sh a_auth`로 임시 DB에 마이그레이션 전체를 적용하고 당신 테스트를 돌립니다. 먼저 `supabase/tests/run.sh _smoke`가 통과하는지 확인하세요.
- 테스트를 먼저 쓰고 구현하세요. 테스트는 실패하면 예외를 던지는 SQL 파일입니다. 사용자 전환은 `select test_login('<uuid>')`, 관리자 복귀는 `reset role;`. 필요한 사용자·프로필 행은 테스트 안에서 관리자 권한으로 직접 넣으세요.
- 다른 흐름의 함수를 부를 때는 plpgsql 함수 안에서만 부르세요(SQL 언어 함수는 만드는 시점에 대상이 있어야 해서 실패합니다). 당신 마이그레이션에서 다른 흐름의 함수를 정의하면 안 됩니다. 테스트에 그 함수가 필요하면 테스트 파일 안에서 `to_regprocedure`로 없을 때만 임시로 만들어 쓰세요.
- 모든 공개 함수에 대해 "다른 사용자로 로그인해서 남의 데이터를 읽거나 바꿔 본다"는 테스트를 넣으세요. 이 프로젝트에서 가장 중요한 테스트입니다.
- 인덱스가 필요한 질의에는 자기 번호대 마이그레이션에서 인덱스를 추가하고, 화면 하나에 필요한 데이터는 함수 하나로 돌려주세요(SRD 4절).
